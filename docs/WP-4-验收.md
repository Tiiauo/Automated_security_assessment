# WP-4 编排与角色引擎：实现与验收

日期：2026-10-22。依据：PRD v1.8、项目规划 WP-4。

## 交付范围

- `RunManager` 管理进程内项目任务、取消信号和启动准入；阶段与角色状态均以 PostgreSQL 为准。
- 按 PRD 15.1 串行执行：
  1. `environment_scan`：环境检查 → 运维辅助；
  2. `code_analysis`：通用处理 → 代码分析；
  3. `vulnerability_verify`：漏洞验证 → 攻击路径整理；
  4. `report_generate`：报告整理 → 通用处理；
  5. `done`：运维归档 → 通用处理 → 调度器销毁容器。
- 每个角色独立落库；原始模型响应、工具参数、工具结果、重试与错误均保留。调用失败和 Schema 失败共用重试预算，重试更新同一条 `worker_tasks`。
- 附录 D1～D6 的 JSON Schema 保存为独立文件，并由测试逐项与 PRD 对照，防止契约漂移。
- 四个工具全部通过远端 Docker exec 执行：目录遍历、文件片段读取、正则搜索、命令执行。路径在容器内执行 realpath 校验；命令具有超时、进程组清理及 1 MB 输出限制。
- 阶段和角色双超时；停止取消当前模型/工具等待，立即终止容器进程并保留容器；启动恢复将残留 running 记录置为 failed。
- 最大并发项目数限制返回 429；同项目重复启动返回 409；运行配置在启动时取快照。
- `GET /api/projects/{id}/stages`、`GET /api/projects/{id}/workers` 已接入鉴权、归属、历史轮次与分页。角色查询还支持阶段和状态过滤。
- 项目详情页轮询真实阶段状态，并移除 M1 阶段的执行引擎占位说明。

## 范围边界

**WP-4 不等同于完整安全评估产品已经交付。**

- 真实模型目前支持环境检查和代码分析，包括候选漏洞基础落库。
- 阶段 3、4 在 `LLM_MOCK=1` 下有通过 Schema 校验的固定响应及漏洞、路径、报告基础写入；所有模拟结果带有明确的 MOCK 标识，验证状态不冒充已验证。
- WP-4 验收时，关闭 MOCK 后未开放的真实漏洞验证和报告生成会明确失败，提示 WP-6 / WP-7，绝不自动降级为模拟成功。
- 后续 WP-6 / WP-7 已接入真实漏洞验证、去重、报告与下载，见 [WP-5 / WP-6 验收](WP-5-WP-6-验收.md)、[WP-7 验收](WP-7-验收.md)；本记录保留 WP-4 当时的验收边界。
- WebSocket、消息/日志/资源查询接口和周期资源采样留给 WP-5；本包已记录每次模型响应的累计 Token，未把占位 CPU/内存值作为实测资源指标。
- 报告前本地源码指纹复核已加在阶段门禁中；源码变化会阻断报告。

## 自动化回归

前提：Docker / PostgreSQL SSH 隧道已建立，数据库可连接，沙箱镜像存在。

```bash
uv run ruff check backend
uv run pytest -q

# 包含真实 Docker 工具、只读源码、输出截断、命令超时及运行中断
SANDBOX_INTEGRATION=1 uv run pytest -q

npm --prefix frontend run build
npm --prefix frontend run lint
```

专项测试覆盖：五阶段十角色顺序、容器销毁时序、Schema 修复及耗尽阻断、原始响应留存、Token 累加、环境检查门禁、双超时、停止幂等与耗时、准备期间停止、并发限制、历史轮次隔离、归属隔离、重启恢复、源码变化和归档/销毁失败。

最终回归：`ruff` 通过，`SANDBOX_INTEGRATION=1 uv run pytest -q` 为 **76 passed**；最后的取消幂等调整又单独复跑生命周期用例，**4 passed**。首次全量执行中，一条既有普通用户鉴权用例曾得到 401 而非预期 403；未改动鉴权逻辑，该用例单独复跑及随后完整复跑均通过，保留此记录便于后续排查偶发问题。

前端 lint 当前仍有 10 条既有警告（Fast Refresh 导出与 effect 中 setState），构建通过；这些警告不属于本包的编排实现范围。

## 独立实机验收

```bash
# 不调用真实模型：真实源码准备、真实容器、MOCK 五阶段、正常销毁
uv run python scripts/verify-wp4.py

# 显式授权调用当前配置的模型，产生 Token 消耗
uv run python scripts/verify-wp4.py --real-model
```

脚本使用独立数据库（当前按进程命名为 `sec_eval_acceptance_<pid>`）与随机高位数字项目 ID，避免与日常项目的命名卷和运行目录混用。不读取用户 `allowed_sources`；只发送脚本新建的最小 Python 程序。模型配置从现有开发库读取，在独立验收库内加密保存；不输出密钥。验收结束清理测试项目、容器、卷与项目目录；独立数据库和系统级审计记录保留供复跑。

已执行的实机结果：

| 验收 | 结果 |
| --- | --- |
| AC-05 / AC-06：真实沙箱 + MOCK 全链路 | 五阶段、十角色全部成功，项目 completed，容器在 done 角色结束后销毁 |
| AC-12：运行中停止 | 模型等待可取消；真实容器 exec 可中断，停止耗时小于 5 秒；重复停止无副作用 |
| 真实模型前两阶段 | environment_scan、code_analysis 均 success；首次覆盖了真实角色重试，复跑确认四个原生工具均实际调用，累计 usage.total_tokens 为 48,893 |
| 真实模型阶段边界 | 前两阶段完成后由验收脚本主动停止；阶段 3 stopped、当前角色 failed 是手动停止的预期状态，不表示前两阶段验收失败 |
| 模型连接探测 | 显式禁用思考模式，并预留 128 Token 的最小工具调用输出预算，避免误判工具能力 |

后续推进 WP-5，继续使用本包的落库记录与真实任务句柄接入实时监控；不要绕过状态源或重新实现另一套编排器。
